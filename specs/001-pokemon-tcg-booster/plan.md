# Implementation Plan: Pokémon TCG 151 Booster Pack Opener

**Branch**: `001-pokemon-tcg-booster` | **Date**: 2026-05-13 | **Spec**: specs/001-pokemon-tcg-booster/spec.md
**Input**: Feature specification from `specs/001-pokemon-tcg-booster/spec.md`

## Summary

Build a pure front-end web game where players open Pokémon TCG 151 set booster packs.
A Python setup script (`download_cards.py`) fetches all ~165 cards from the pokemontcg.io
API (set sv3pt5), saves each image as `.jpg` into one of 7 rarity-based `assets/` folders,
and emits a `assets/data/cards.json` manifest the browser app loads at runtime.

The browser app draws 6-card packs using a mulberry32 seeded RNG following slot-specific
rarity probability rules, reveals cards one at a time via Space/click with CSS 3D flip
animations, and persists the collection in localStorage. A tab toggle switches between
the pack-opening view and a full 165-card collection grid (silhouettes for unowned cards,
image + copy count for owned). Auto-reset after the 6th reveal restarts the loop.

## Technical Context

**Language/Version**: JavaScript ES2022 (browser) · Python 3.10+ (setup script only)
**Primary Dependencies**: Vite 5 (dev server + static bundler) · Vitest (unit tests)
**Storage**: `localStorage` — JSON-encoded collection map `{ cardId: copyCount }`
**Testing**: Vitest + jsdom; distribution tests over 10,000 seeded packs (seed `42`)
**Target Platform**: Browser (Chrome/Firefox/Safari latest), iOS Safari, Android Chrome
**Project Type**: Pure front-end web app — static files, no server runtime
**Performance Goals**: Full 6-card reveal < 10 s active play; collection filter < 1 s
**Constraints**: Offline-capable after initial asset download; zero backend; all images local
**Scale/Scope**: 165 cards · 7 rarity tiers · single player · unlimited packs per session

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

- [x] **I. Pure Front-End** — Vite produces a static `dist/` directory; no server runtime
  introduced. `download_cards.py` is a developer tool, not a runtime dependency.
- [x] **II. Client-Side Persistence** — Collection stored exclusively in `localStorage`
  under key `ptcg_collection` as JSON. No remote calls at runtime. Strategy documented
  in `contracts/storage-schema.md`.
- [x] **III. Testable Probabilistic Distribution** — mulberry32 seedable RNG implemented
  in `src/modules/rng.js`. Vitest distribution tests for slots 5 and 6 use seed `42`
  over 10,000 packs, asserting ±2 pp deviation from specified probabilities.
- [x] **IV. Mandatory Responsiveness** — CSS Grid/Flexbox layouts designed for
  320 px / 768 px / 1024 px breakpoints. Validated via Vitest + jsdom viewport simulation
  and manual visual review.
- [x] **V. Organised On-Disk Assets** — Card images under `assets/<NN_folder>/`,
  data manifest at `assets/data/cards.json`. No other asset locations used.

**Post-design re-check**: All gates still pass after Phase 1 design. No violations.

```text
├── download_cards.py                 # Developer setup script (Python 3.10+)

├── assets/
│   ├── data/

│   ├── 03_raras/                     # Rare / Rare Holo images (*.jpg)

│   ├── main.js                       # Entry point: app init, tab routing
│   ├── modules/
│   │   ├── rng.js                    # mulberry32 seedable RNG (pure function, no DOM)
│   │   ├── pack.js                   # Pack generation: slot rules, uniqueness, draw
│   │   ├── collection.js             # localStorage read / write / query
│   │   └── ui/
│   │       ├── packView.js           # Pack opening view: reveal loop, animation states
│   │       └── collectionView.js     # Collection grid, rarity filters, counter
│   └── styles/
│       └── main.css                  # All styles; CSS custom properties for theming
│
└── tests/
    ├── rng.test.js                   # Determinism, seeding, uniform distribution

```

**Structure Decision**: Single front-end project at repository root (no backend directory).
`src/modules/` separates pure logic (rng, pack, collection) from DOM-coupled view code
(`ui/`), keeping the core modules independently testable without jsdom.
